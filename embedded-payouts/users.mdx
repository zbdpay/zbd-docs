A user is the same object in Embedded Payouts and Embedded Accounts, so a user you create for payouts stays the same user if you add an economy later.

You create users from your backend, and ZBD verifies them. Each user has a verification tier and a payment method.

## When to create and verify

You can create and verify users up front, or when they need it.

|   | Up front | Just in time |
| --- | --- | --- |
| What happens | Create and verify users before anyone earns | Create when someone earns, verify when a payout requires it |
| Suits | A known set of users, contracted creators, programs where payout is expected | Large pools of casual earners where most never reach a payout |
| Trade-off | Friction for people who may never cash out | Friction lands at the moment someone wants their money |

Whichever you choose, a user has to exist before you can [credit them](/embedded-payouts/how-payouts-work), and has to be verified before a [payout](/embedded-payouts/paying-out) above their current tier.

## Creating a user

Create a user with your own identifier for them. You don't need any personal data at this stage.

## Verification

Verification is tiered. A user's tier sets how much they can be paid, and they can move up a tier as their earnings grow or when you prompt them.

You decide where verification appears in your product, and ZBD tells you when a payout needs a higher tier than the user has. Verification always runs through ZBD, in the widget's identity verification flow.

## Tax information

ZBD collects tax information when a payout requires it, or at onboarding if you'd rather collect it early. ZBD works out which form applies based on where the user is and where you are. It's collected once, so users aren't asked again.

## Payment method

The user chooses how they want to be paid from the [options available in their country](/embedded-payouts/methods-and-coverage), in the widget's payment method selection flow. ZBD collects and holds the details.

A user can hold a balance before choosing a payment method, but can't be paid until they have one.

## Reading user state

You can read a user's tier, whether they have a payment method, and whether they can be paid right now. That's usually enough to decide what to show them, like a cash out button, a prompt to verify, or a prompt to add a payment method.
